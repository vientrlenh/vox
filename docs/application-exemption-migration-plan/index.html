Application exemption migration plan

Repository: vox · Branch: default · Written 2026-11-21 · Plan status: Done

59 classes in application/ are listed in APPLICATION_EXEMPTIONS of LayeredArchitectureTests because they still use a framework or library type that AGENTS.md keeps out of that layer (Spring DAO and transaction types, @Value, Jackson, POI, @Async, servlet and security types, and so on). This plan moves each of those usages behind a port in application/port/output (or removes it where it is dead or replaceable by an allowed type, or moves the code to the layer that owns it), so that APPLICATION_EXEMPTIONS ends empty in both LayeredArchitectureTests and LombokUsageConventionTests. It changes no REST, GraphQL, Kafka, database or configuration contract. AGENTS.md asks for exactly this: “those lists may only shrink, so remove a class from them when you fix it”.

Findings that shape the design

  • DataIntegrityViolationException (36). The 27 use cases contain 28 catch sites that rethrow 12 DuplicatedException (message differs per site), 9 IllegalStateException and 7 IllegalArgumentException. The 9 import commit handlers have 7 sites that record a failed row and 2 that rethrow IllegalStateException. Neither GlobalExceptionHandler nor GlobalExceptionResolver mentions DataIntegrityViolationException or DataAccessException: an unmapped exception ends in the generic 500 / INTERNAL_ERROR. Outside application/ the exception is caught 15 times in 14 files (all in infrastructure, none in interfaces): 10 event consumers wrapping processedEventRepository.save, and 4 adapters (AssessmentCandidate twice, AssessmentProctoringAlert, AssessmentScheduleProctor, Notification); none wraps the repositories behind these 36 classes. Precedent for translating in an adapter: AssessmentCandidateRepositoryImpl throws DuplicatedException.
  • Some of these catches may never fire (suspected, not run). 27 of the 36 classes are @Transactional and the 9 import handlers are not. AGENTS.md says “the insert is sent at flush, not at save()”. Of the adapters behind these sites, the ones I read for the plain save / saveAll paths (Framework, FrameworkCriterion, FrameworkResultBand, SupportedLanguage, SchoolGrade, SchoolClassUser, RubricCriterion, RubricResultBand, GradeLevel) do not flush, so a unique-index violation would surface at commit, after the use case's try block. The sites that can fire are the @Modifying atomic updates (updateGradeLevelAtomic, updateCriterionAtomic, updateResultBandAtomic, updateRubricVersionAtomic), UserRepositoryImpl.saveAndFlush and the import handlers (the commit happens inside TransactionTemplate). The plan migrates every catch as it is, proves which are live (job 8.2), and reports the rest; it does not change flush behaviour (see Out of scope).
  • Transactions (10 classes, 16 execute / executeWithoutResult calls). Every TransactionTemplate is set to PROPAGATION_REQUIRES_NEW and no lambda uses its TransactionStatus (grep setRollbackOnly|TransactionStatus finds 0). One port with run and call covers all of them. Two of the ten are money paths: SubmitPracticeTurnUseCase (quota consumption) and CreatePaymentCheckoutUrlUseCase (payment checkout) – see D2.
  • Jackson (6). JsonSerializationPort already has 8 methods; commit 734d6f3b extended it the same way (port + JacksonJsonSerializationService + FakeJsonSerializationPort + JacksonJsonSerializationServiceTests). The four shapes are: a JsonNode inside a port record (sourceJson, never read inside application/; only PracticeQuestionGenerationClient writes and reads it), read one string field, parse a List<String>, and typed read/write. UpdateSchoolRubricCriterionUseCase and UpdateSystemRubricCriterionUseCase hold a near-identical 12-line block that does new ObjectMapper() (Jackson 2, com.fasterxml) parse of List<RubricCriterionExample> and re-serialise RubricCriterionExamples; this is duplicated logic, so the plan extracts it once. The port's mapper is the Spring-configured Jackson 3 mapper, so the stored string could differ (R3).

2. Decisions

Each of these is on the AGENTS.md “Ask first” list (a new file outside the listed patterns, a payment or quota path, OAuth/refresh-token code, deleting a file) or has several workable shapes.

D1. How does application code learn that the database rejected a write? (replaces DataIntegrityViolationException in 36 classes) Answered

A. (recommended) A new DataConflictException in application/exception (a new file outside the patterns listed in “Ask first”, hence this question). Persistence adapters, through one shared helper, and the new transaction adapter translate Spring’s exception into it. Use cases catch it and throw exactly what they throw today. REST and GraphQL do not map it, so a caller that does not catch it still ends in the same generic 500 as today. Cost: one new exception, one helper, edits to the adapters behind the 27 use cases.

B. Reuse DuplicatedException as the carrier (no new file; precedent AssessmentCandidateRepositoryImpl). Trade-off: any caller that does not catch it would answer 409 / BAD_REQUEST instead of 500 (a visible API change, including on the payment and quota paths that use the transaction port), and a foreign-key or not-null violation would be reported as a duplicate.

C. Defer the 36 classes: keep their names in the list and do phases 1–7 only (23 classes leave).

Answer (2026-11-21): A – new DataConflictException (recommended).

3. Phases

Each phase is independently reviewable and leaves the build green. Phases 1–7 do not depend on each other except where a phase says so; phase 8 is last because it uses the transaction adapter from phase 4 and finishes classes that phases 2 and 3 only half-fixed. You can stop after any phase.

Rules for every job (they come from AGENTS.md; jobs do not repeat them):

1. Remove the migrated class’s name from LayeredArchitectureTests.APPLICATION_EXEMPTIONS in the job that removes its last violation; delete a group comment when its group becomes empty; never add a name. 2. Behaviour stays the same: no change to REST/GraphQL responses, event payloads, DB schema, or config keys and env var names. If a job finds it cannot keep that, it stops and asks. 3. New ports go in application/port/output with no Spring or library type in the signature; implementations go in infrastructure (model: QuotaPricingPort / QuotaPricingService). Logic shared by several use cases goes in application/port/input/service/. 4. Methods stay at most 25 lines; explicit types instead of var. 5. Translate every Vietnamese comment in code a job edits into English, keeping its meaning and its “why”; leave user-facing string literals (exception messages) as they are. 6. Tests: Mockito with @ExtendWith(MockitoExtension.class), strict stubs, no lenient(); @RepositoryTest for adapters; classes named XxxTests in the mirrored package. Existing tests that hand-build a class keep their style; they are not converted as a drive-by. 7. Every job also runs ./gradlew compileJava and ./gradlew test --tests '*LayeredArchitectureTests' --tests '*LombokUsageConventionTests'.

        4. Risks

The port keeps the same executor (security context passed on, CallerRunsPolicy when the queue is full) and logs exceptions; 5.1 tests both. The two services stay public beans called from other beans, as before.

        • R9. Size. 39 jobs across 8 phases, with phase 8 alone adding 21 new use-case or handler test classes (5 + 2 + 1 + 5 + 4 + 4) plus adapter tests. Each phase leaves the build green and the list shorter, so the work can stop or be reviewed in pieces.
