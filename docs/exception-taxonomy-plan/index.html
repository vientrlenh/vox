Exception taxonomy plan

Repository: vox · Branch: default · Written 2026-11-23 · Plan status: Done

Shrink the exception vocabulary to what the code really distinguishes. Three exceptions that all mean “the request is valid but a business rule says no” (PlanLimitExceededException, QuotaExceededException, WalletDrawConfirmationRequiredException) become one BusinessRuleViolationException. InfrastructureException becomes plain IllegalStateException, which means “internal fault, answer 500”, so the handler that turns IllegalStateException into 400 is removed and every bad request is an IllegalArgumentException. NotFoundException and DuplicatedException are renamed ResourceNotFoundException and ResourceDuplicatedException. It is worth doing because today IllegalStateException is used for two opposite things (a client mistake in 565 application sites, a server fault in 78 infrastructure and interface sites) and both answer 400.

D2. What does BusinessRuleViolationException look like on the wire? Answered

It is a new class (no AGENTS.md pattern covers it) and changes public error codes of quota and plan-limit code paths, so AGENTS.md Ask first applies. Only the thrown type changes; no quota arithmetic is touched.

A. (recommended) One class, one constructor (String message). REST 422 with code BUSINESS_RULE_VIOLATION; GraphQL BAD_REQUEST with extensions code BUSINESS_RULE_VIOLATION; gRPC FAILED_PRECONDITION. It is what you asked for and the simplest. Cost: the table in 1.3. In particular the frontend cannot use the code to decide to show the “confirm wallet draw” dialog any more, and quota exhaustion changes from 409 to 422. Confirm the clients are updated.

B. Same as A but REST answers 409 CONFLICT. Keeps the status of quota exhaustion; changes plan limit and wallet draw from 422 to 409.

C. One class that carries a string code (BusinessRuleViolationException(String code, String message)) so the three old codes survive on the wire. No client break for codes, but the three code strings stay alive at the throw sites and a code registry has to be invented, which keeps most of what you wanted to remove.

Answer (2026-11-23): A – One class with (String message); REST 422 BUSINESS_RULE_VIOLATION, GraphQL BAD_REQUEST with extensions code BUSINESS_RULE_VIOLATION, gRPC FAILED_PRECONDITION. The table in 1.3 is accepted.

D3. Which errorCode does a failed practice paper draft get for a business rule violation? Answered

PracticePaperDraftService stores errorCode = QUOTA_EXCEEDED only for QuotaExceededException, to tell the client the failure is not worth retrying. That field is documented in practice-planning.graphqls:46, so it is a GraphQL contract. After D1 the service can no longer tell quota exhaustion from a plan limit (for example “school has no active subscription”, thrown by the same flow).

A. (recommended) Every BusinessRuleViolationException gets BUSINESS_RULE_VIOLATION. Both cases are equally not retryable, and the code matches the REST one. The schema description example and PracticePlanningResponses:71 are updated.

B. Every BusinessRuleViolationException keeps the literal QUOTA_EXCEEDED. Clients keep working unchanged, but plan-limit failures are mislabelled as quota.

Answer (2026-11-23): A – Every BusinessRuleViolationException gets errorCode BUSINESS_RULE_VIOLATION.
