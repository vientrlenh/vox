GraphQL inputs, keys and data loaders restructuring plan

Repository: vox · Branch: default · Written 2026-11-24 · Plan status: Done

Five changes, none of which edits the GraphQL schema text (the fifth changes what a request does, see D8 and the risks): (1) the four mutations that take a raw Map<String, Object> take records whose omit-able fields are Spring’s ArgumentValue<T>; (2) graphql/dto/request becomes graphql/input and the DataLoader key records leave application for graphql/key; (3) graphql/config is split into dataloader and scalar, and the 57 loaders are regrouped so that each schema’s config registers every loader that returns its types (51 loaders after merging 6 duplicates), under one naming rule; (4) every env.getDataLoader(...) goes through one shared method that throws IllegalStateException when the loader is not registered; (5) the 17 existing update inputs with nullable fields use ArgumentValue, so a client can leave a field alone (omit it) or clear it (send null) where the column allows it. Worth doing because today the same user is loaded by three differently named loaders, a missing loader is a NullPointerException at 74 of the 78 call sites, and the loader code is spread over 13 files that do not match the schema files.

2. Decisions

D1. Scope of the request and how this plan reads it Answered

Decided in the request: the four changes listed at the top. The plan reads them like this, and approving the plan confirms the readings:

  • ArgumentValue. It is Spring’s org.springframework.graphql.data.ArgumentValue, used on every component of the 4 input records (all their schema fields are nullable PATCH fields). The application commands keep their value + valueProvided pairs, because application may not import Spring (LayeredArchitectureTests); the record’s static toCommand turns !isOmitted() into the flag. What a client sends and gets back does not change.
  • Packages. graphql/dto/request/<feature>/ becomes graphql/input/<feature>/ with the same 14 sub-packages; the key records go to graphql/key; graphql/config becomes graphql/dataloader (the 13 loader configs and PageKey, which is a grouping helper and not a loader key) and graphql/scalar (DateScalarsGraphQLConfig). Moves use git mv so history follows.
  • Loaders. A loader is registered in the config of the type it returns, loaders with identical behavior are merged (6 of them), and the name follows <result>By<KeyField> (userByUserId). The example usersByUserIds is read as naming style: no loader of that shape is created, because no object-type field resolves users from a list of user ids (grep -n '\[ID' src/main/resources/graphql/*.graphqls finds only query and mutation arguments such as teacherIds, studentIds, excludeUserIds, one input (offeredTopicIds) and one query that returns school ids). Granularity of “config per type”: D3.
  • The 20-record rule. “Types expected to retrieve more than 20 records use a key and a repository method” is read as: a loader that returns many children per parent takes a key with page and size, and its repository has a per-parent windowed method like the three that exist. Which loaders qualify is D7.
  • The check. One shared method looks the loader up and throws IllegalStateException when it is missing (D6 decides where it lives). The type fits AGENTS.md “Errors”: a missing loader is a wiring fault the caller cannot cause or fix, and GlobalExceptionResolver already answers an IllegalStateException as INTERNAL_ERROR (its last branch).
Answer (2026-11-24): As requested – taken from the task description. The readings above are mine and are confirmed by approving the plan.

D3. Where does a loader live: one config per schema file, or one per result type? Answered

A. (recommended) One config per schema file, named after it, holding every loader whose result type is defined in that .graphqls file: 12 configs (table in 1.2). user.graphqls defines both User and Role, so UserGraphQLDataLoaderConfig holds userByUserId, usersByRoleId and rolesByUserId. Biggest files: Assessment 15 loaders, School 8, Framework 6. A reader goes from the schema file to the config with the same name.

B. One config per result type: 41 configs by my count (SchoolClassGraphQLDataLoaderConfig, AssessmentPaperGraphQLDataLoaderConfig, RubricCriterionGraphQLDataLoaderConfig, ...). Every file is small and each constructor is short, which makes D4 trivial. The cost is many files with 1–3 loaders, Assessment’s 15 loaders spread over about 11 files, and a reader has to know the exact type name to find a loader.

Answer (2026-11-24): One config per schema file – the recommended option.

D4. How does a config register its loaders within the 25-line method limit? Answered

AGENTS.md: a method is at most 25 lines (30 for a very large feature), signature to closing brace. Today each config registers everything in its constructor. After D3 = A, Assessment has 14 repositories and 15 loaders and School 8 and 8, so no explicit constructor can fit. The repository has no @PostConstruct today, so option A is a new pattern.

A. (recommended) @RequiredArgsConstructor with private final fields (the registry and the repositories), and one @PostConstruct method that calls one private registerXxx() per loader, each at most 25 lines. This is exactly AGENTS.md’s constructor rule (an assignment-only constructor becomes Lombok), a slice test that @Imports a config still works because Spring calls the method, and no signature carries 14 parameters.

B. Keep explicit constructors; each loader is a private static method taking (registry, repository...) and the constructor only calls them. No new pattern, but it only fits configs with few repositories: Assessment (and School) would have to be split by type, which is D3 = B for those configs.

Answer (2026-11-24): @RequiredArgsConstructor + @PostConstruct – the recommended option.

D5. Loader names: constants or string literals? Answered

The request renames loaders (userById becomes userByUserId). 78 main call sites and about 20 test stubs change either way.

A. (recommended) Every name is a public static final String in its owning config (UserGraphQLDataLoaderConfig.USER_BY_USER_ID); registration, controllers and tests use the constant and never a literal. A typo or a missed rename then fails to compile instead of failing when a client first resolves that field.

B. Same new names, written as string literals at registration and at every call site. A smaller diff per line and no new members in the configs, but a wrong name is found only at request time (the check from D6 makes that error clear, but it is still at runtime).

Answer (2026-11-24): Constants in the owning config – the recommended option.

D6. Where does the shared loader check live, and is it guarded? Answered

A new class does not fit the file patterns in AGENTS.md “Ask first”, so it is a decision.

A. (recommended) A final class GraphQLDataLoaders in interfaces/graphql/dataloader with static <K, V> DataLoader<K, V> require(DataFetchingEnvironment environment, String loaderName) that returns the loader or throws IllegalStateException("DataLoader not registered: " + loaderName). Plus a guard test GraphQLDataLoaderConventionTests (source-text scan like PagingConventionTests) that fails when getDataLoader( appears in src/main/java outside that class and, with D5 = A, when a loader is registered with a literal or a name is registered twice.

B. The same class without the guard test. Less to maintain, but nothing stops the next controller from calling env.getDataLoader(...) directly.

C. A protected method on an abstract base class for the 17 controllers. They share no base class today, and inheritance would couple them for one helper. Not recommended.

Answer (2026-11-24): GraphQLDataLoaders + guard test – the recommended option.

D7. Which loaders become keyed (paged) with a new repository method? Answered

The 17 loaders that return an unpaged list (16) or read a list to return one value (1), judged from the domain, not from production counts:

  • Can pass 20 per parent: assessmentSchedulesByAssessmentId (one session per room and time slot of an assessment; the assessment list page reads all of them to draw the scheduling progress bar, so paging it would break that page), assessmentMembersByAssessmentId (CHAIR, AUTHOR, REVIEWER of one assessment; usually below 20 but not bounded by the model).
  • Reads far more rows than it returns: assessmentSchoolClassIdByAssessmentId loads every candidate of every assessment on the page (a class-sized assessment has as many candidates as students) to keep one student id per assessment.
  • Bounded by the model or the domain: framework criteria, result bands and criterion bands; order items; payments of an order; question assets, collaborators and bank grades (a bank has at most a few grade levels); register form documents; plan quotas; paper sections and items; papers of an assessment; roles of a user.

The 6 loaders that already have a key (school classes, school users, users by role, rubric versions, criteria, result bands) are relocated and renamed in every option.

A. (recommended) No GraphQL change. Give assessmentSchoolClassIdByAssessmentId a repository method that returns only the first candidate per assessment (row_number() OVER (PARTITION BY assessment_id ORDER BY assigned_at, id), the same pattern as the 3 existing windowed queries), so it stops reading every candidate. The class id it returns is unchanged; “first” becomes deterministic (today findByAssessmentIdIn has no ORDER BY, so the first row is whatever the database returns).

B. A, plus paged keyed loaders for Assessment.schedules and Assessment.members: two new keys, two windowed repository methods, and new page/size arguments on two schema fields. That is a GraphQL contract change (AGENTS.md “Ask first”): the frontend must pass the arguments, results are cut to the default page size, and the progress bar that reads all schedules needs another source.

C. Relocate and rename only; no new repository method. The 20-record rule is not applied to anything new and assessmentSchoolClassIdByAssessmentId keeps reading every candidate.

Answer (2026-11-24): Fix only the candidate loader – the recommended option.

      4. Risks

      • Omitted versus null drifts in the four inputs. This is the one semantic the Map existed to protect (avatarUrl: null removes an avatar). Each job in phase 2 proves it through the real binder for the fields that matter, and job 2.1 runs first because it has the most existing coverage; if spring-graphql 2.0.4 does not bind ArgumentValue in a record the way the 2.0.5 source reads, the phase stops there and the plan is revised.
      • A missed loader rename fails only when a client resolves that field. The constants (D5) make it a compile error, and the guard test plus GraphQLDataLoaders.require catch a literal or an unregistered name.
      • Slice tests lose a loader. Moving a loader to another config means a slice test that imported the old config no longer registers it (for example AssessmentGraphQLTests after the school-room loader moves). Compilation will not show it; the jobs name the slice tests to run, and the rule “a slice test imports the config that owns the loader” is in every loader job.
      • Merged loaders share one cache and batch. One DataLoader now serves what three did, so a request makes fewer queries and one user is loaded once; the repository call and mapper were identical, so results do not change. The guard in schoolDataLoader for an empty id set is dropped because a DataLoader never calls its batch function with no keys.
      • A new pattern (D4). @PostConstruct registration is not used elsewhere in the repository; job 6.1 is the first use, so a problem shows early.
      • Behavior change for existing clients (D8). Two things now behave differently for the same request: a client that omits a group-2 field (passingScore, strictness, effectiveTo, a framework or scoring-rule description) now keeps it instead of clearing it, and a client that sends an explicit null for one of the 14 clearable group-1 fields (1.4) now clears it instead of keeping it. A form that sends null for an untouched field would wipe data after the release. The plan cannot make old and new clients both safe; table 1.4 is the checklist for the frontend, and phases 12–16 are independent so each can be held back.
      • SQL with an optional clear. CASE WHEN :fieldProvided ... :field with a null parameter can fail on Postgres (“could not determine data type of parameter”) and the 9 statements bypass auditing (they set updated_at/updated_by themselves). The @RepositoryTests catch the first (they need Docker and run in integrationTest, not in ./gradlew test); each job keeps the existing audit columns in its statement.
      • Wider commands. 21 commands gain 1–3 flags each; tests that construct them positionally stop compiling, which is how the missing updates show up. A flag that no use case reads is a bug, so rule (4) in phases 12–16 requires a test per flag.
      • The REST rubric update. UpdateSystemRubricRequest is the only REST record that builds an affected command; if it forgets to set the flag, REST starts clearing descriptions on a plain null. Job 14.1 names it and tests it.
      • The candidate loader’s “first” becomes deterministic. Today findByAssessmentIdIn has no ORDER BY, so which candidate comes first is up to the database; the new method orders by assigned_at, id. If every candidate of an assessment is in the same class (the loader’s premise) the result is unchanged; if classes are mixed, it now picks the earliest assigned one consistently.
      • Money and security areas. Order, invoice, payment and subscription loaders are renamed and re-registered, nothing more. No payment, quota, balance, JWT or security configuration is touched; @PreAuthorize annotations on controller methods are left as they are.
      • Large diff. 50 files move (27 inputs, 8 keys, 15 config files), 17 controllers and at least 7 test files change for the loaders, 12 configs are rewritten, and phases 12–16 touch 21 commands, 22 use cases, 9 SQL statements, 17 input records and every test that builds those commands. Every phase leaves the build green and is reviewable alone; moves use git mv so review can follow them.
