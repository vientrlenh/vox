GraphQL typed scalars and enums plan

Repository: vox · Branch: refactor/rewritten · Written 2026-11-20 · Plan status: Done

Today every GraphQL schema file in src/main/resources/graphql declares timestamps, dates and status/type values as String, and the Java side mirrors that with String fields in DTOs and responses, plus hand-written parsing in controllers. This plan makes the schema say what the data is: Instant becomes a DateTime scalar, LocalDate becomes a Date scalar, status/type values become schema enums, and BigDecimal money values stay String. The DTOs, responses, inputs and controller arguments that carry these values change to the real Java types in the same slices, so the string parsing and .toString() glue can be deleted.

D3. How strict scalar input parsing is Answered

Input delegates to DateMapper.toInstant / DateMapper.toLocalDate, so the web client's date-only and offset-less values and the extra date formats keep working until the existing compatibility branch is removed on its own schedule. The schema description says the strict form is the contract. Only possible with D2 = A.

B. Strict input: DateTime requires an offset, Date requires yyyy-MM-dd. Cleanest contract, but the policy and framework forms that send effectiveFrom: "2026-07-28" fail with a coercion error on day one, so the frontend must ship first or together.

Answer (2026-11-20): Strict ISO only. DateTime input needs an offset (Z or ±HH:MM), Date input is yyyy-MM-dd. GraphQL no longer goes through DateMapper's compatibility branch, so date-only values such as 2026-07-28 are rejected: the frontend must send full timestamps at the same time as the cutover (D6).

3. Phases

Each phase is independently reviewable and leaves the build green. Mapping rule used by every module job, so it is written once here:

  • A field gets DateTime when the Java value is an Instant (or a String that is parsed with DateMapper.toInstant), and Date when it is a LocalDate (or parsed with DateMapper.toLocalDate / LocalDate.parse). A name like startDate does not decide it; the Java type does. If the Java type is unclear, stop and ask.
  • A field becomes an SDL enum named after the Java enum's simple name (required by GraphQlEnumParityTests), following D5. The enum is declared once, in the schema file of the module that owns it, and values are copied from the Java enum.
  • Money amounts (*Vnd, costUsd, fxRateUsed and other BigDecimal values) stay String. month: "YYYY-MM" and JSON-in-string fields stay String.
  • In every job the Java carriers (domain/dto, application/response, application/query/dto, interfaces/graphql/dto/request, commands/queries), the controller arguments and mappers change with the schema, @Argument and input records take the real types, and manual parse/toString() glue that this makes dead is deleted. Vietnamese comments and schema descriptions in edited code are translated to English, and descriptions that say "ISO string" or "format YYYY-MM-DD" are rewritten to match the new type.
  • Each module job adds or extends a test that sends a query through the real schema with a typed variable and asserts a DateTime/Date/enum value in the response (an @GraphQlControllerTest with the use case mocked), and a wrong enum or date value is rejected as a GraphQL validation/coercion error rather than a 500.

      4. Risks

      • Breaking client operations. Variables declared as String stop validating once an argument is an enum or scalar. Limited by D6 (one coordinated cutover) and the change list in job 9.3.
      • Enum drift. An SDL enum that misses a Java constant fails at serialization time, not at startup; a Java String value that is not an SDL enum constant fails the same way. GraphQlEnumParityTests catches the first class and every module job tests a real value; both rely on the parity test running, which needs Docker (integrationTest).
      • Silent REST change. Changing shared DTOs could alter REST JSON or the OpenAPI schema. Limited by job 1.3 (pinned before the change) and the REST test run in every phase. The OpenAPI document does change shape (string to enum/date-time format); that is not a JSON change but it is visible to REST consumers.
      • Timezone. Instant output is UTC. Tests must not depend on the default timezone (AGENTS.md); date-only compatibility input is resolved in the business zone by DateMapper, not by the JVM default.
      • Strict input breaks existing forms. Because D3 is strict, the web client's date-only effectiveFrom/To values (the reason DateMapper has a temporary compatibility branch) and any dd/MM/yyyy input are rejected on GraphQL after the cutover. REST still goes through DateMapper and is unchanged. The frontend change list in job 9.3 must call this out first.
      • New dependency compatibility. graphql-java-extended-scalars versions track graphql-java versions; a mismatch with the 25.0 that Spring Boot 4.1.0 brings fails at startup. Job 1.1 checks the release against graphql-java 25.0 and stops if none fits.
      • Existing slice tests stop building once the schema declares a scalar with no wiring. Covered by job 1.2 before any field changes.
      • Mapping mistakes from field names. A field named startDate can be an Instant. The mapping rule follows the Java type, and an unclear case stops the work.
      • Size. Roughly 290 schema fields, 65 domain DTOs and 27 input records across 28 schema files. Limited by module-sized jobs, a pilot checkpoint (2.4) and a green build after every phase.
