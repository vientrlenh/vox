Interfaces naming and packaging plan

Repository: vox · Branch: default · Written 2026-11-23 · Plan status: Approved

Make the interfaces layer easier to navigate and consistent with the use-case layout. Four changes, none of which alters behaviour, URLs, the GraphQL schema, Kafka topics or the database:

  1. Every REST controller becomes RestXxxController and every GraphQL controller GraphQLXxxController. Every other class name that spells GraphQl or Graphql with a lowercase l becomes GraphQL.
  2. The commands, the queries and the request records move from one flat package each into feature sub-packages that use the same names as the use-case packages (usecase/assessment, usecase/rubricsystem, ...).
  3. The command and query mapper classes of the interfaces layer are replaced by static methods on the request records, written as public static XxxCommand toCommand(XxxRequest request).
  4. Test classes follow the class they test, and the guard tests and AGENTS.md are updated so the new layout cannot drift back.

It is worth doing because today 20 simple class names exist twice (AssessmentController in both the REST and the GraphQL package, which is why 25 GraphQL controllers carry hand-written bean names), 304 commands and 150 queries sit in two flat folders, and 131 + 20 mapper classes sit between a request and the command it becomes.

  • GraphQL schema. No class name appears in a .graphqls file except in one comment (assessment.graphqls:902); fields bind by schema name, so the schema is unchanged.

2. Decisions

D1. Direction of the change, and the exact shape of the conversion methods Answered

Decided in the request: the four changes listed at the top. The plan reads them like this, and approving the plan confirms the readings:

  • Prefix. “Rest + xxxController” means the word is put in front of the existing name. The two internal controllers become RestAssessmentTurnInternalController and RestPracticeSessionInternalController. A test class follows the class it tests (RestAuthControllerTests, GraphQLAssessmentControllerTests), as AGENTS.md already says (“XxxTests in the mirrored package”). The 35 XxxGraphQlTests keep their subject-based names and only change GraphQl to GraphQL.
  • Packages. Sub-package names are exactly the 53 use-case feature names. A command or query goes where its same-name use case is; the existing sub-packages (assessmentevaluation, practiceevaluation, key) stay; otherwise the one feature whose use cases import it; the rest follow D6. A request record goes with the command or query it becomes; a nested record goes with its parent; an unmapped one goes with the use case its controller method calls.
  • Methods. One conversion on a record is toCommand (or toQuery). Path ids and caller data come first and the request last, which is the order the mappers use today. A record with several conversions names each to<CommandClassName> (for example toAcceptRubricCriterionImportCommand); overloads by parameter list are allowed. A list conversion is toCommands(List<XxxRequest>). The body is moved unchanged.
public record UpdateAssessmentRequest(/* components unchanged */) {

    public static UpdateAssessmentCommand toCommand(UUID assessmentId, UpdateAssessmentRequest request) {
        return new UpdateAssessmentCommand(assessmentId, request.name(), /* ... as in the mapper today ... */);
    }
}

3. Phases

Each phase is independently reviewable and leaves the build green. They run in the order written: the small renames first, the large moves in the middle, the conversion of mappers once records and commands already sit in their final packages, the guards and the documents last.

Rules for every job. (1) Mechanical edits are done with a throwaway script kept in the scratchpad, never committed; it reads and writes bytes so the CRLF working tree is not rewritten. (2) Moves use git mv (two steps through a temporary name when only the case changes) so history follows. (3) Import lines are edited in place; nothing is re-sorted or reformatted, and no unused code is cleaned up. (4) A Vietnamese comment on a declaration or statement that the job edits or moves is translated to English, faithfully; string literals stay as they are. (5) After each job ./gradlew compileJava compileTestJava is green.

                                                                    4. Risks

                                                                    • Case-only renames get lost. core.ignorecase=true here, Linux in CI. Limited by two-step git mv in jobs 1.1 and 1.2 and by the greps over git ls-files in their done-conditions, which read the index, not the working tree.
                                                                    • 914 files change an import in phase 4 and 145 + 27 main files in phase 5. A script can miss a same-package use, a wildcard or a Javadoc link. Limited by the 41 hidden dependencies already counted in 1.4, by a green compileJava compileTestJava after each job, and by running the whole unit suite after phase 4.
                                                                    • The same simple name exists on both sides. For the 20 names in 1.2 a text replace of AssessmentController is wrong for half of the files. The scripts of jobs 2.1 and 3.1 decide by package and import, never by name alone, and comment mentions in files that import neither class are decided by reading them.
                                                                    • A moved conversion changes silently. A wrong field order still compiles when two fields share a type, and only 26 of 33 REST controllers have a controller test. Limited by moving bodies unchanged and by a scratchpad script that compares every moved body with the old mapper body apart from its signature; mismatches are fixed by hand and noted.
                                                                    • OpenAPI tags would change for all 33 REST controllers, and a consumer that keys on a tag would break. Limited by the customizer of job 2.3 (D3) and its test; not checked against a running app (needs Postgres, Redis, Kafka).
                                                                    • Logger and bean names change for the renamed classes (log searches, alerts by logger name). Not limited in code; listed in the final report as cross-system impact.
                                                                    • Conflicts with parallel work. The plan renames or moves about 1,000 files. test-restructuring-plan (phases 4-5 open) edits the same test classes. Limited by running this plan on its own branch from default and finishing or pausing that work first; open pull requests were not checked.
                                                                    • Placement is a judgement call for 22 shared or unreferenced types. Limited by D6 and by recording every target in the implementation notes.
                                                                    • Static methods on records. A static method is not a record component or a bean property, so Jackson, Bean Validation, springdoc and Spring GraphQL ignore it. Limited by RestRequestTypesTests and the GraphQL tests (which bind the real schema) in each phase.
                                                                    • Windows line endings. The tree is CRLF and the index LF. Limited by byte-level script I/O (rule 1) and by git diff --stat showing only the intended files per job.
