2. Decisions

D1. Scope of the request and how this plan reads it Answered

Decided in the request: three changes. The plan reads them like this, and approving the plan confirms the readings:

Item 1 (builders). Application code stops calling Model.builder() on a domain model. Each call becomes a named public static factory or an instance method on the model, which still builds itself with its own builder() (AGENTS.md requires the nested Builder; infrastructure mappers, domain code and tests keep using it). Setters, new Model() (5 sites) and immutability are untouched.

Item 2 (stamps). A repository method stops receiving a value only to write updated_at or updated_by: the 17 methods in the table of 1.2, and their callers and tests. How they stop is D2 and which parameters count is D3.

Item 3 (method rules). A method is migrated when it is longer than 25 lines (AGENTS.md "Small functions"; the allowance of 30 is not used as a blanket exemption) or when its name is one of the vague words AGENTS.md lists (19 methods). "Names that describe how they work" is applied to every extracted or renamed method; "remove comments if they violate the rules" is applied inside every method the plan edits: a comment that only restates the code (// 1. Validate the user) is deleted; a comment that records a reason (a race, a security rule, a workaround) is kept and translated faithfully to English, as the Language rule demands.

Order. Stamps first (small, and it settles what repository methods look like), then builders (new model API), then method size by feature area, so that the long methods are already shorter when they are split.

Answer (2026-11-24): As requested – taken from the task description. The readings above are mine and are confirmed by approving the plan.

D2. How do the 17 stamp-passing repository methods lose their parameters? Answered

Today @Modifying statements bypass the JPA auditing hook, so 15 domain repository methods take an updatedAt or updatedBy parameter (two more take a now that also feeds updated_at) and 27 call sites compute Instant.now() and currentUserId.toString() for them. AGENTS.md "Audit columns" says they "still set updated_at/updated_by themselves", so any answer here also changes that sentence (D5). None of the 12 entities involved has @Version (it exists only on Order, SubscriptionPlan and SchoolBalance).

A. (recommended) Keep the single-statement updates; remove the stamp parameters from the domain interface, adapter, use case and test. The adapter takes the time and the actor from one infrastructure source that follows the auditing rule (actor of the active scope, else the authenticated user, else "System"). Atomic guards (WHERE status = ..., queue claims) behave exactly as today; use cases lose two arguments and two locals each. Trade-off: the methods still exist, only their parameters go, and the stamp is computed in the adapters (one small infrastructure class or one method on AuditActorProvider).

B. Delete the update methods: the use case loads the model, calls a new model method (for example schoolRoom.update(...)), and save lets the hook stamp it. Cleanest result and the closest to item 1, but the 16 live single-statement updates become read-modify-write of whole rows: with no @Version a concurrent edit is last-write-wins on every column, the DRAFT/PREVIEWED/PENDING guards become check-then-write races, and the import queue claim loses its atomicity.

C. Hybrid by kind: B for the 9 plain edits whose use case already loads the row and has no status guard (School, SchoolRoom, SchoolGrade, SchoolClass.updateMutableFields, SupportedLanguage, GradeLevel, and the three rubric updates) plus deleting the dead markImporting; A for the 7 guarded, queue or bulk statements. Removes 10 methods, keeps the guards. Trade-off: two patterns to maintain, and the 9 plain edits still lose per-column atomicity.

Answer (2026-11-24): A – Keep the single-statement updates; remove the stamp parameters from interface, adapter, use case and test; the adapter takes the time and the actor from one infrastructure source that follows the auditing rule.

D3. Which parameters count as the "same behaviour" as updatedAt / updatedBy? Answered

The request says "or any their same behaviour attributes". The code has three kinds of parameter next to the stamps, listed in 1.2.

A. (recommended) Only values that end in updated_at / updated_by: the 13 pure-stamp methods lose both parameters, and the 4 mixed ones lose only the stamp half (RegisterForm approve/reject lose now and the reviewer id is renamed reviewerId, because it writes reviewed_by; markClaimed keeps now for claimed_at; requeueExpiredLeases keeps now as the lease predicate). The 7 methods whose now writes a business column (readAt, revokedAt, usedAt, ...) are not touched.

B. Also the 7 business-timestamp methods stop receiving Instant now; their adapters read the clock. Moves the moment of a business event (when a notification was read, a token used) out of the use case, needs an injectable clock in adapters to stay testable (there is no Clock bean and Instant.now() appears 271 times in main), and widens the blast radius to 7 more methods and their tests.

Answer (2026-11-24): A – Only values that end in updated_at / updated_by; the 7 business-timestamp methods are not touched.

D4. What are the new model methods called? Answered

AGENTS.md says to ask when a pattern is ambiguous. Today 28 of the 104 models have 42 factories: create x11, createFresh x3, forTopUp x2 and 26 one-off names (seeded, suspended, forQuotaFunding, emptyFor, createByAdmin).

A. (recommended) Intent-named: one static factory or instance method per distinct set of call sites, named for the situation it builds, for example ImportSession.previewed(...), ImportRow.pending(...), AssessmentPaperItem.forQuestion(...) and AssessmentPaperItem.emptySlot(...), item.copyInto(paperId, sectionId). create only when a model has exactly one way of being created. Identical call shapes share one method (the 17 import sessions become one). Matches the request's "names that describe how they work" and the majority of existing factories.

B. Uniform create(...) / of(...) with overloads. Easier to guess and find, but different situations share one name and only the parameter list tells them apart, and it contradicts the naming rule the request asks to prioritize.

Answer (2026-11-24): A – Intent-named factories and instance methods, one per distinct set of call sites.

3. Phases

Each phase is independently reviewable and leaves the build green. Phase 1 adds the guards, phase 2 removes stamp parameters, phases 3 to 12 add model methods and replace call sites, phases 13 to 28 split methods by feature area, phase 29 closes out. Every job also removes the imports, locals and private methods its change orphaned, and translates the Vietnamese comments in the lines it edits.

Procedure of a method-rule job (phases 13 to 28). Every method over 25 lines is split into private methods of at most 25 lines, named for what they do (D1, D7). A block that already exists in two or more methods is extracted once into a shared method in application/port/input/service/ (the AGENTS.md "one place" rule) and named in the Implementation notes. Statements move verbatim: same order, same conditions. Comments that only restate the code are deleted; those that record a reason are kept and translated to English; the school-scope and role checks are never rewritten. The done condition is always the same: the job's entries leave method-size-exemptions.txt and MethodSizeConventionTests passes.
