REST typed request inputs and malformed-request handling plan

Repository: vox · Branch: refactor/rewritten · Written 2026-11-20 · Plan status: Approved

REST controllers and the command records behind them still take enum-like and date-like values as String. A client typo in status or openAt is then caught late and unevenly: a @Pattern regex on the request record, a hand-written valueOf or DateMapper call in a mapper or use case, or an unhandled exception that becomes a 500. This plan moves those inputs to their real types (enum, Instant, LocalDate), swaps the regex guards for the right validation annotations, and makes GlobalExceptionHandler answer every malformed request with a clear 4xx instead of a 500. GraphQL inputs are already covered by the in-progress graphql-typed-scalars-plan and are not repeated here.

1. Current state (measured)

Request side (REST)

  • 154 request records in interfaces/rest/dto/request (ls | wc -l), and 131 files in interfaces/rest/mapper that copy them into commands.
  • 62 record components typed String whose name looks like an enum or a date (status, type, kind, scope, mode, role, platform, method, decision, period, *At, *Date, from, to, until, deadline), in 42 files. This is a name-based grep, so it is a heuristic and it undercounts (it misses dateOfBirth in 4 request files: CreateSchoolRequest.adminDateOfBirth, CreateSchoolUserRequest, RegisterBySelfDeclaredRequest, RegisterFromSchoolDirectoryRequest): each job produces the exact list for its own slice. Only 6 request fields are typed Instant (all deadlineAt/occurredAt) and a handful are typed enums (CreateScoringRuleRequest.conditionType/actionType, TokenPurchaseItemRequestItem.quotaType, UpdateFrameworkVersionStatusRequest.status, CreateAssessmentRequest.resultDecisionMethod), so the typed form already exists and is the pattern to repeat.
  • 31 @Pattern annotations in 29 request files. 30 of them only list constants (regexp = "STUDENT_DEVICE|LAB", "FIXED|SELECTION", ...), which is an enum written as a regex. One validates a code format and stays (CreateFrameworkRequest, ^[A-Z0-9_-]+$). Ten records carry an action verb string (UpdateAssessmentStatusRequest, UpdateQuestionStatusRequest, BulkUpdateQuestionStatusRequest, ...); only one was searched for a matching Java enum so far (PUBLISH_RESULTS appears only in UpdateAssessmentStatusUseCase and its request, no enum), so the other nine are checked job by job, which is D5.
  • Query and path parameters: 68 @RequestParam, of which 20 are String (AssessmentController status/sort, AssessmentResultController resultStatus/roundType/assignmentStatus/kind twice, AuthController deviceId/deviceName/platform, QuestionController scope/type/contentType/topicName/keyword). 3 @PathVariable are String: NotificationController.installationId (a free id, stays) and SubscriptionController.quotaType twice (a QuotaType enum value). No controller uses @Validated (grep -rln prints nothing).
  • Validation annotations in request records today: @NotBlank 159, @NotNull 143, @Size 114, @NotEmpty 37, @Valid 36, @Min 32, @DecimalMin 13, @Email 6. All user-facing messages are Vietnamese.

Application side (shared with GraphQL)

  • 76 String components with enum/date-like names in 57 command/query records (application/port/input/command|query). The REST mappers pass request Strings straight into them, so a request record cannot become typed without its command (D1). Counts are of the current tree, which already includes the GraphQL plan's work through its Phase 7.
  • 61 X.valueOf(...) calls on enums in use cases and services under application/port/input (for example AssessmentMemberRole.valueOf(command.role()), AssessmentBlueprintSlotType.valueOf(...) 9 times, QuotaType.valueOf 5 times, GradingRoundType.valueOf 3 times), and 18 DateMapper.to* calls in application code plus 22 in 11 REST mappers. Some import handlers (QuestionImportCommitHandler, AssessmentPolicyImportCommitHandler) parse cell text from uploaded files; those are not request inputs and stay.
  • Some of these parsers are lenient (.trim().toUpperCase() in AddSchoolRubricVersionsUseCase, AddSystemRubricVersionsUseCase, GetAssessmentRecordsUseCase, RecordAssessmentAttemptEvaluationUseCase), while the matching @Pattern guards are strict. A real enum type forces one choice (D2).
  • DateMapper.toInstant accepts offset timestamps and, through a documented temporary compatibility branch, offset-less date-time and date-only values; DateMapper.toLocalDate accepts four formats. Both exist because the web client sends date-only values for effectiveFrom/To (D3).

Error handling today

  • GlobalExceptionHandler (interfaces/rest/exception) handles 16 exception types. It has no handler for HttpMessageNotReadableException (bad JSON, unknown enum constant, wrong value type, unparsable date), MethodArgumentTypeMismatchException (bad UUID/enum/date in a path or query value), MissingServletRequestParameterException, HandlerMethodValidationException or HttpMediaTypeNotSupportedException (grep -rn over src/main and src/test finds none). It does have @ExceptionHandler(Exception.class), so these very likely fall through to handleGeneric: HTTP 500, an ERROR log line and the body "Có lỗi xảy ra". Not measured yet; job 1.1 proves it before anything is built on it.
  • handleIllegalArgument returns e.getMessage() with 400. When a use case's valueOf fails, the client therefore receives the JDK text "No enum constant com.sep.vox.…", which exposes internal class names.
  • handleValidation builds its map with err.getObjectName() as the key. For a @RequestBody that is the object name (for example createAssessmentRequest), not the field, so several field errors overwrite one another and the client cannot tell which field failed. The response shapes are ErrorResponse(error, message) and ValidationErrorResponse(errors, message="BAD_REQUEST").
  • Test coverage: 17 REST slice test classes exist; none asserts a malformed-body, bad-enum, bad-date or bad-parameter response. AuthControllerTests:109 is the only one that asserts the validation body.
  • GraphQL malformed input: graphql-java rejects wrongly typed variables and scalar values before any data fetcher runs, so GlobalExceptionResolver needs no new handler for that. Covered by graphql-typed-scalars-plan.

2. Decisions

D1. How far does the type change reach? Answered

A. (recommended) End to end: request record, command/query record and use case all use the real type, so the valueOf/DateMapper glue in the touched use cases and REST mappers is deleted. GraphQL mappers that build the same command are adjusted in the same job. One source of truth and no .name() round trip, but each job touches more files.

B. Request records only: type them and convert back with .name()/.toString() in the REST mapper. Smaller diffs, but it keeps the String parsing in 61 use-case sites and defeats the goal.

Answer (2026-11-20): End to end – request record, command/query and use case all use the real type; the valueOf/DateMapper glue in touched files is deleted and GraphQL mappers are adjusted in the same job.

D2. Enum matching: exact name or case-insensitive? Answered

A. (recommended) Exact constant name everywhere, which is what every @Pattern enforces today. Where a use case is lenient today (toUpperCase() in the rubric and recording use cases), that leniency goes away and is listed for the frontend change list.

B. Case-insensitive for JSON bodies (a Jackson enum feature) and for query/path values (a converter). Keeps the lenient endpoints working, but changes global binding for every endpoint and needs a new configuration class (a file that fits no pattern).

Answer (2026-11-20): Case-insensitive – enum constants are accepted in any letter case for JSON bodies and for query/path values. Approves one small configuration (a property in application.yaml or a new config class, whichever job 1.4 finds works); no other global binding change.

D3. How strict is date and timestamp input on REST? Answered

A. (recommended) Strict ISO-8601, the same contract the GraphQL plan chose: Instant needs an offset (Z or ±HH:MM), LocalDate is yyyy-MM-dd. Uses Jackson's and Spring's built-in handling with no custom code. Date-only effectiveFrom/To values and dd/MM/yyyy are rejected with 400, so the frontend must change at the same time (D8).

B. Keep today's tolerance: add a custom deserializer and query converter that delegate to DateMapper. Nothing breaks for clients, but it adds new classes (no existing pattern), keeps the temporary compatibility branch alive and leaves two different contracts for REST and GraphQL.

Answer (2026-11-20): Strict ISO – Instant needs an offset (Z or ±HH:MM), LocalDate is yyyy-MM-dd; date-only effectiveFrom/To and dd/MM/yyyy are rejected with 400, so the frontend must change at the same time.

D4. Shape of the error response for malformed requests Answered

This changes a public API contract (AGENTS.md "Ask first": anything consumed by the frontend).

A. (recommended) Keep both existing shapes. Malformed body/parameter/path/media-type errors return 400 (415 for media type) as ErrorResponse or ValidationErrorResponse with Vietnamese messages that name the field and, for enums, the accepted values, and never include class names. Also fix handleValidation to key errors by field name instead of object name, so several invalid fields are all reported. Clients that read message or error keep working; only the map keys of validation errors change.

B. Same as A but leave handleValidation keyed by object name, and report the collapsing as a known problem. No change to existing 400 bodies; new errors use the same weak keying.

C. Move to RFC 9457 ProblemDetail (Spring's built-in response for these exceptions). Standard, but a new body shape for every error and a bigger frontend change.

Answer (2026-11-20): Keep shapes, key by field – ErrorResponse and ValidationErrorResponse stay; new malformed-request handlers name the field and list accepted enum values; handleValidation is fixed to key errors by field name.

D5. Fields that have no matching Java enum Answered

The ten action fields (publish/archive/approve verbs), plus values such as targetBandLevel and streamType lists, have no enum with the same constant set.

A. (recommended) Convert a field only when an enum with exactly the same constants already exists. Others keep String and their @Pattern guard, and are listed in the implementation notes. No new domain types and no guessing at value sets; the same rule as D5 of the GraphQL plan.

B. Also create new enums for the closed action sets (about 10 files). Fuller result, but new files that fit no pattern, with an open question of where they live (domain/model or application), and each value set must be checked against what the use cases accept.

Answer (2026-11-20): Leave as String – convert a field only when a Java enum with exactly the same constants already exists; the rest keep String and their @Pattern, and are listed in the implementation notes. No new domain types.

D6. Touching money and authentication code Answered

Phase 9 changes request, command and use-case types for quota, subscription plans and payments (QuotaType, SubscriptionPlanPeriod, DistributionMode, payment provider and method). Phase 10 changes the login and OAuth platform parsing and the stream-token requests. AGENTS.md puts money logic and JWT/OAuth code under "Ask first".

A. (recommended) Allow phases 9 and 10, limited to field types, parameter types, validation annotations and the valueOf glue. No amounts, quota or balance logic, no token issuing or claims, no security config.

B. Skip phases 9 and 10 and list them as follow-up work. Nothing sensitive is touched, but the quota, payment and login endpoints stay String-typed.

Answer (2026-11-20): Allow, types only – phases 9 and 10 run, limited to field types, parameter types, validation annotations and parsing glue. No amounts, quota or balance logic, no token issuing or claims, no security config.

D7. When does this plan start, given the unfinished GraphQL plan? Answered

A. (recommended) Start phase 2 after graphql-typed-scalars-plan is done (its phases 8 and 9). Phase 1 touches only the REST exception handler and can start now. Job 2.1 re-measures the command records first, because the GraphQL plan will already have typed some of them.

B. Run both on this branch in parallel. Faster, but both plans edit the same command records, GraphQL mappers and shared DTOs, so every job risks a merge fight and duplicate edits.

Answer (2026-11-20): After the GraphQL plan – phase 1 (REST exception handler only) may start now; phases 2–11 start once graphql-typed-scalars-plan is done, and job 2.1 re-measures the command records first.

D8. How is the REST contract change released? Answered

Valid requests keep their JSON text (enums by name, ISO-8601 dates). What changes is the status and body for invalid input and, with D3 = A, the rejection of date-only and non-ISO dates.

A. (recommended) All phases on this branch, one merge, one frontend change list written in job 11.2. Matches the cutover the GraphQL plan chose, so the frontend migrates once.

B. Merge phase by phase, each with its own frontend change. Smaller releases, but REST would be half-migrated for a long time and every merge needs frontend coordination.

Answer (2026-11-20): One cutover – all phases on this branch, one merge, one frontend change list from job 11.2.

D9. Add a guard test so String inputs do not creep back? Answered

A. (recommended) One test that scans interfaces/rest/dto/request and the REST controller parameters and fails when a component is a String named like *At, *Date, effectiveFrom/To, status, type, platform, etc., with an explicit allow-list for the D5 leftovers. Same kind of guardrail as PagingConventionTests: a String field passes every behavioural test. It is a new test file that fits no existing pattern.

B. No guard. Fewer files, but the next request record can quietly reintroduce String openAt.

Answer (2026-11-20): Add the guard – one new test file RestRequestTypesTests (job 11.1) with an allow-list limited to the D5 leftovers.

3. Phases

Each phase is independently reviewable and leaves the build green. Rules every job in phases 2–10 follows, so they are not repeated:

  • Per field: use the type the domain already uses (Instant for timestamps, LocalDate for calendar dates, the existing Java enum). Check the enum's constants equal the old @Pattern list before converting (D5). Replace @NotBlank with @NotNull on the converted field (@NotBlank is invalid on an enum or date), delete the @Pattern that listed the constants, and keep the Vietnamese message on the new @NotNull. Do not add business rules (for example opens-before-closes) that do not exist today.
  • Per request-to-use-case path (D1 = A): request record → command/query → REST mapper → GraphQL mapper (if any) → use case. Delete the valueOf or DateMapper call that became redundant, in the files the job already edits, and nothing else.
  • Per job tests: a @RestControllerTest case for a valid value, one for an unknown or malformed value answering 400 in the shape fixed by D4, and one for a missing required value. Use cases are @Mock/@MockitoBean. Where the endpoint group has no authorization test yet, report it; do not widen the job.
  • Comments in edited code are translated to English; functions stay at 25 lines or fewer; no var in new code; user-facing Vietnamese messages stay.

                                                                                4. Risks

                                                                                • Breaking REST clients. Strict dates (D3 = A), the rejection of unknown enum values and the new 400 bodies change what clients may send and see. Limited by D8: one merge with one frontend change list, and by job 11.2 listing every changed field.
                                                                                • Collision with graphql-typed-scalars-plan. Both edit commands, shared DTOs and mappers. D7 = A sequences them; job 2.1 re-measures before editing.
                                                                                • REST and GraphQL disagree on case. With D2 REST accepts sum or SUM, while GraphQL enums stay exact. Documented in the frontend change list (job 11.2); the contract is lenient on input only, responses always use the constant name.
                                                                                • A command shared with GraphQL. Typing a command breaks the GraphQL mapper that builds it. Each job compiles the whole module and the GraphQL slice tests for the same feature, and adjusts the GraphQL mapper in the same job.
                                                                                • Enum constants differ from the old regex. A converted field must accept exactly what the @Pattern accepted. Each job compares the constants before converting and leaves the field as String (D5) when they differ.
                                                                                • A wrong handler hides real bugs. Catching too broad a type would turn server bugs into 400s. Phase 1 maps only the five Spring web exceptions listed, never RuntimeException, and the existing handleGeneric still logs ERROR for everything else.
                                                                                • Jackson 3 behaviour is assumed. Defaults for unknown enum constants, null, numbers coerced into enums and Instant parsing are not yet verified; job 1.1 measures them and any surprise (for example numeric ordinals accepted) is handled in 1.2 before the migration phases.
                                                                                • Money and auth code. Phases 9 and 10 touch it only with D6 = A and only at the type level; use-case arithmetic, token issuing and security config are explicitly off limits.

                                                                                5. Out of scope

                                                                                • GraphQL schema, inputs and scalars (graphql-typed-scalars-plan). GraphQL error handling needs no change for malformed input.
                                                                                • Response types: no response record or DTO output type changes here.
                                                                                • 404 (unknown route) and 405 (wrong method) responses, even though they likely share the same fall-through to 500 today. Reported, not changed.
                                                                                • The free-form sort query parameter (AssessmentController:127), keyword, names, free text and ids such as installationId.
                                                                                • File-import parsing of cell text (QuestionImportCommitHandler, AssessmentPolicyImportCommitHandler, ImportFieldMappingRequest.dateFormat) and the DateMapper compatibility branch itself.
                                                                                • New business validation (opens-before-closes, future-only dates, length limits) that does not exist today.
                                                                                • New dependencies, a Jackson/MVC global configuration class (unless D2 = B is chosen), and any change to SecurityConfig, JWT or OAuth code.
                                                                                • Noticed, not fixed: GlobalExceptionHandler.handleDisabled is declared private although it is an @ExceptionHandler; the class Javadoc and several comments are Vietnamese (translated only in code a job edits).
