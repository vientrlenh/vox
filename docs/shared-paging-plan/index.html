Shared paging plan

Repository: vox · Branch: refactor/rewritten · Written 2026-11-20 · Plan status: Done

Every paged request enters the system 1-based and must be rejected when page < 1. Today that rule is re-implemented in about 30 places, and the conversion to and from Spring Data's 0-based pages is written by hand in every adapter (page - 1 on the way in, getNumber() + 1 on the way out, and in 8 places the + 1 is missing). This plan puts each of the three steps behind one shared method: validate the request page at the boundary, subtract 1 when calling Spring Data or building an offset, and add 1 back when building the response. Then a guard test keeps it that way.

1. Current state (measured)

Measured on 2026-11-20 on branch refactor/rewritten (clean tree). ./gradlew compileJava passes, so the plan takes on no existing compile failure. The unit and integration suites were not run for a baseline (not checked).

Request side (validation)

  • interfaces/shared/PageArguments.validate(Integer page, Integer size) already exists. It rejects page == null || page <= 0 and a size outside 1..200 with IllegalArgumentException, and it has PageArgumentsTests. It is called from 5 controllers (AssessmentAppeal, AssessmentDirectory, Dashboard, Grading, REST AssessmentController). Command: grep -rn PageArguments src --include='*.java'.
  • The other controllers do not use it. There are 17 private validator methods in 16 controller files (validatePage, validatePageSize, validatePaging, requireValidPaging), plus 33 ad-hoc page <= 0 / < 1 / < 0 lines under interfaces/ (grep -rnE "page *(<=|<) *(0|1)\b" src/main/java/com/sep/vox/interfaces). Their size rules differ (most accept any size > 0, only PageArguments caps at 200).
  • They do not agree on the rule: 4 validators accept page == 0 (page < 0 in AssessmentController, AssessmentBlueprintController, QuestionController, QuestionBankController); those requests would later fail inside Spring Data with PageRequest.of(-1, ...). 2 controllers silently clamp a bad page to 1 (ScoringRuleController, 8 lines in 4 methods; SchoolController, 2 lines). They throw a mix of IllegalArgumentException and IllegalStateException (both become BAD_REQUEST in GlobalExceptionResolver) with different Vietnamese messages.
  • RoleController.roleUsers passes page into a DataLoader key with no check at all.
  • Entry points: 23 GraphQL controller files, 112 @Argument(name = "page") parameters, 132 page: Int arguments in src/main/resources/graphql/*.graphqls. REST has exactly 1 paged endpoint (GET /api/v1/assessments), and it already validates.

Subtract side (to Spring Data / SQL offset)

  • 51 hand-written PageRequest.of(page - 1, ...) calls in 32 adapter files under infrastructure/persistence/adapter (grep -hE "(page|pageNumber) - 1" adapter/*.java | wc -l gives 52 lines: the 52nd is UserRoleRepositoryImpl.findByRoleIdIn, which builds a 1-based row range with (page - 1) * size + 1). Calls of the form PageRequest.of(0, limit) are "top N", not paging, and stay.
  • Query repositories compute offsets by hand: 11 matching lines in 9 files under infrastructure/persistence/query: 6 setFirstResult((page - 1) * size) and 4 native .setParameter("offset", (long) (page - 1) * size) (SchoolAiCost, SchoolWorkload, SchoolsAtRisk, GradingFailure). JpaAssessmentGradingQueryRepository has two matching lines; the job inspects each. Two of them (Directory, StudentAssessment) also clamp with Math.max(page, 1).

Response side (add 1 back)

  • PageResult (domain/common) is constructed 120 times in 91 files. Most adapters echo the request's 1-based page, which is already correct. 15 sites read Spring's 0-based getNumber(): 7 add 1 (School 1, Framework 2, FrameworkVersion 2, Rubric 2) and 8 do not (RubricCriterion 2, RubricVersion 2, RubricResultBand 2, Rubric 2). So the first page of those Rubric queries answers page: 0 while the schema is 1-based.

Guardrail and tests that exist

  • PagingConventionTests scans source text: adapters must contain PageRequest.of(x - 1 (needs >30 scanned methods), query repositories must contain setFirstResult(... - 1 (needs >4), GraphQL page defaults must not be 0. It nails the convention but also hard-codes the hand-written - 1, so it must be retargeted when the subtraction moves into a helper (D6).
  • Only 3 adapter tests exist (src/test/.../infrastructure/persistence/adapter) and 20 query tests (most are @RepositoryTest, need Docker). Controller tests exist for Question, School, MyClass, SupportedLanguage, AssessmentAppeal, Import.
  • Layering: LayeredArchitectureTests forbids interfaces -> infrastructure and application -> infrastructure/interfaces. The application layer does not convert pages (only comments mention it), so the shared subtract/add-1 code belongs in infrastructure, and the validator stays in interfaces/shared.

2. Decisions

D1. Where the three rules live Answered

Already decided by the request: the request page must be validated at the boundary (page >= 1) by one shared method; the page is converted to Spring's 0-based value by one shared method; the response page is converted back to 1-based by one shared method.

Answer (2026-11-20): Decided in the request – "the page should not be lower than 1 … it will be subtract by 1 using a shared method as well (the response must plus 1 back using a shared method as well)".

D2. Where does the subtract / add-1 helper live? (new file outside the usual patterns) Answered

A. (recommended) One new final class infrastructure/persistence/paging/OneBasedPaging with static methods toPageRequest(page, size), toPageRequest(page, size, sort), toOffset(page, size) and toPageResult(springPage, content). Cohesive, the only place that knows Spring's 0-based convention, allowed by LayeredArchitectureTests (adapters and query repositories both live in infrastructure). Costs one new file that fits no X + Command/Query/... pattern.

B. No new file: add static int helpers to the existing domain/common/PageResult and keep PageRequest.of(...) written out in each adapter. Smaller footprint, but the Spring conversion is still repeated 51 times, so "one place" is only half true.

Answer (2026-11-20): A – New OneBasedPaging class

D3. Does the shared request validator also take over the size rule? Answered

A. (recommended) Page only. Add PageArguments.validatePage(Integer page) (rejects null and values below 1) and make the existing validate(page, size) call it. Each controller keeps its own size check. Matches the request and changes no size behavior.

B. Page and size: route every controller through the existing PageArguments.validate(page, size). Removes more duplication, but introduces the 200-row cap on the ~12 controllers that have none today. That is a public API contract change.

Answer (2026-11-20): B – Page and size. Every controller calls PageArguments.validate(page, size); a size above 200 or a null size is now rejected everywhere.

D4. What happens to requests that are accepted today with a bad page? (API behavior change) Answered

Affected: the 4 controllers that accept page = 0 and ScoringRuleController / SchoolController (2 sites) that clamp a missing or non-positive page to 1. All errors become IllegalArgumentException with the PageArguments message.

A. (recommended) Reject everywhere. One rule for the whole API, as the PageArguments Javadoc already argues (clamping hides wrong input). Clients that send 0 or omit page on the clamping queries will now get BAD_REQUEST; the frontend must be checked.

B. Reject only where a validator already throws; keep the clamping in ScoringRuleController and the two SchoolController sites, and still reject 0 in the 4 controllers. No new break for clamping clients, but "page < 1 is invalid" is no longer true everywhere.

Answer (2026-11-20): A – Reject everywhere

D5. Which response sites use the shared add-1 method? (API behavior change) Answered

A. (recommended) Every site that reads Spring's 0-based getNumber() (15) goes through toPageResult. That fixes the 8 Rubric sites so the page field of the response becomes 1-based (first page answers 1, not 0), as the schema promises. Adapters that echo the request page (already 1-based) are left alone. A regression test proves the fix. The frontend must not depend on the 0 value.

B. Only wrap the 7 sites that already add 1, and leave the 8 Rubric sites returning 0-based. No client-visible change, but the inconsistency stays and the shared method does not cover the whole response side.

Answer (2026-11-20): A – All getNumber() sites, fix the 8

D6. How is the guardrail PagingConventionTests changed? (architecture rules are never loosened) Answered

A. (recommended) Retarget it to a stricter form of the same convention: adapters and query repositories must use OneBasedPaging and must contain no hand-written - 1 / PageRequest.of( / getNumber(); a new boundary rule requires every method with a page argument to call PageArguments, and forbids ad-hoc page <= 0 checks. The "scanned > N" self-checks stay. The test must change either way, because the old rules look for the hand-written subtraction that this plan removes.

B. Keep the old regexes and make them accept either form (helper or manual - 1). Simpler, but looser: a new adapter could bring back a hand-written subtraction and still pass.

Answer (2026-11-20): A – Retarget, stricter

D7. Record the new convention in AGENTS.md? (changing AGENTS.md needs your confirmation) Answered

A. (recommended) Yes: edit the "Pagination is 1-based at every boundary" bullet to name PageArguments and OneBasedPaging as the only places allowed to validate and convert. It is the tracked place for this decision, so it is not lost.

B. No: leave AGENTS.md as it is and rely on the guard test and this plan.

Answer (2026-11-20): A – Yes, update the bullet

4. Risks

  • Client-visible changes. D4-A makes page 0 and "missing page on a clamping query" return BAD_REQUEST, D3-B makes a size above 200 or a null size return BAD_REQUEST on every controller (about 12 had no cap; the schema defaults are 10 or 20 and no in-repo caller asks for more than 200), and D5-A changes the page field of 4 Rubric queries from 0-based to 1-based. The final report lists all three as cross-system impact for the frontend and desktop app.
  • Error text and type change. Controllers that threw IllegalStateException or their own message now throw IllegalArgumentException with the PageArguments message. Both map to BAD_REQUEST in GraphQL; the only paged REST endpoint already uses PageArguments. The frontend must not match on the old text.
  • Silent wrong page. A missed or wrong conversion returns the wrong rows with no error (this is why PagingConventionTests exists). Mitigation: OneBasedPaging throws on page < 1, the guard test is retargeted in the same phase that makes the old one obsolete, and each phase greps for leftover - 1.
  • Text-scanning guard. Regex rules can miss unusual formatting. Their "scanned > N" self-checks stay so a broken regex fails loudly.
  • Docker. Query and repository tests are @RepositoryTest. If Docker is not available, Phases 2 and 3 are verified only by compileJava, unit tests and the grep checks, and the report says so.
  • Size of the diff. About 33 adapter, 9 query and 20 controller files, mostly mechanical. The jobs are grouped so that each is reviewable alone.

5. Out of scope

  • The Math.max(page, 1) and size clamps inside JpaAssessmentDirectoryQueryRepository and JpaStudentAssessmentQueryRepository. They are reported, not changed. The size cap value (200) itself is not changed.
  • PageRequest.of(0, limit) / PageRequest.ofSize(1) "top N" calls, and adapters that echo the request's 1-based page into PageResult (already correct; D5-A).
  • The 120 PageResult constructions in use cases and mappers, the GraphQL schema (page defaults), proto and Kafka contracts.
  • The stale Javadoc in ViewMyAssessmentsQuery ("numbered from 0") is wrong for the 1-based convention but sits in a file the plan does not otherwise edit; it is reported in the final report.
