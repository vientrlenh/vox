UUID v7 ids for every entity row Vox creates

Repository: vox · Base: default (HEAD ad7e632c) · Written 2026-11-24 · Priority: runs before model-methods-and-method-rules-plan (paused after its phase 7) · Plan status: Draft

16 JPA entities declare @Id with no generator, so the application invents their ids with UUID.randomUUID() (version 4) at 18 sites in 17 files, and their tables have no DEFAULT uuidv7(). This plan gives those entities Hibernate's @UuidGenerator(style = VERSION_7), the declaration that 54 other entities and BaseEntity already use, removes the 18 sites, and adds a guard so a new entity cannot fall back to version 4. It is worth doing because ids then sort by creation time (the same property the rest of the schema already has) and one rule, not 16 adapters, decides how an id is made.

The cause is the missing generator, not the missing BaseEntity. A v7 id needs only @Id @UuidGenerator(style = VERSION_7). Extending BaseEntity would also add four audit columns, and none of the 16 tables has all four (13 have none, 3 have only created_at); AGENTS.md says such a class “is not given the missing columns”. D1 asks whether you still want them to extend BaseEntity.

This plan goes beyond AGENTS.md in one sentence (Database: “Entities whose id the application assigns (UUID.randomUUID() in the adapter) keep it”), and it touches practice papers, which reserve quota seconds. Both are listed in section 1.8 and asked as D3 and D5. Nothing may start until D1 to D5 are answered.

1.4 What a preset id does to a generated entity, and the documentation check

  • Question: does Hibernate also need @GeneratedValue next to @UuidGenerator? No. Checked in the Hibernate 7.4.1.Final sources (Gradle cache, the version this project resolves): @UuidGenerator is meta-annotated @IdGeneratorType(org.hibernate.id.uuid.UuidGenerator.class); GeneratorBinder.createIdGeneratorsFromGeneratorAnnotations installs the id generator from that annotation first, and reads @GeneratedValue only in the final else if. The @IdGeneratorType javadoc says the JPA @GeneratedValue is not used there and the generator annotation “itself implies that id is a generated value”, and names @UuidGenerator as the complete example. So @GeneratedValue would be redundant (not re-tested here).
  • The repository agrees: 0 entities use @GeneratedValue (the only 2 matches in src/main/java are comments), 55 files use @UuidGenerator alone (54 entities and BaseEntity), and ./gradlew integrationTest --tests '*GradingTaskDetailQueryTests' --tests '*SupportedLanguageAuditingTests', which persist such entities with null ids, passed on 2026-11-24.
  • A preset id is ignored by a generated entity. AbstractSaveEventListener.generateId hands the preset id to the generator only when Generator.allowAssignedIdentifiers() is true (default false; only Assigned overrides it, org.hibernate.id.uuid.UuidGenerator does not), so a merge of a new row that carries UUID.randomUUID() gets a different id from the generator. Spring Data calls merge for a non-null id (rule recorded in the earlier base-model-audit plan, not re-read). That is why every job below changes the entity and its call sites together: one without the other compiles and still misbehaves.
  • UuidVersion7Strategy keeps a last-timestamp and sequence state so ids stay monotonic inside one JVM (read in the same sources). Two queries order by id: TurnCorrection findByTurnIdOrderById and TopicInterestEvent findByStudentIdOrderByOccurredAtAscIdAsc (tie-break). With v4 the order is random; with v7 it follows creation. Existing rows keep their v4 ids.

2. Decisions

D1. How do the 16 entities get v7 ids? Open

The 16 entities do not extend BaseEntity because they lack its audit columns (section 1.2).

A. (recommended) Declare @Id @UuidGenerator(style = UuidGenerator.Style.VERSION_7) on each of the 16, the declaration the 54 other non-base entities use and that AGENTS.md prescribes (“declare it on an entity that does not extend it”). No schema change except the safety-net default of Phase 2, no audit columns invented, BaseEntity untouched.

B. Make the 16 extend BaseEntity. Adds created_at, updated_at, created_by, updated_by to the tables that lack them (13 have none, 3 have only created_at), with migrations and a backfill of NOT NULL columns that invents timestamps for old rows, and the 16 entities, mappers and models change. It contradicts the audit rule in AGENTS.md and decision D2 of the finished base-model-audit plan. Choose it only if you want an audit trail on these tables; the plan would then be rewritten around migrations.

C. New abstract BaseIdEntity (id only, @MappedSuperclass, @SuperBuilder) that the 16 extend. One id declaration for the 16, but a new file that fits no AGENTS.md pattern, and the 54 existing entities keep their own declaration, so two ways to declare an id coexist.

Not answered yet.

D2. What happens to AssessmentItemResponse, whose id the AI service supplies? Open

Section 1.6: most rows carry the AI service's answerId; only withoutRecording (the backfill of unanswered questions) mints an id in Vox.

A. (recommended) Leave this one entity as it is: assigned id, no generator, and AssessmentItemResponse.withoutRecording keeps UUID.randomUUID(). It becomes the single documented exemption of the new guard (job 7.1). Reason: the table's ids are mostly the AI service's v5 values, so v7 would cover only a minority of its rows, and the change would sit on the grading hot path. Jobs 6.3 and 6.4 are then marked Deferred.

B. Add a custom Hibernate id generator that keeps a preset id and otherwise makes a v7: two new files in infrastructure/persistence (an @IdGeneratorType annotation and a BeforeExecutionGenerator whose allowAssignedIdentifiers() returns true and that delegates to UuidVersion7Strategy.INSTANCE), proven by a test first (jobs 6.3, 6.4). Result: no UUID.randomUUID() row id is left in src/main. Cost: two files that fit no pattern, custom code on the grading path, and the AI service's v5 ids are still not v7.
